# Application document quality

Use when creating or editing a CV, resume, cover letter, or supporting statement file.

## File workflow

- Confirm the requested file type and destination from the user's request. If either is optional, choose a reasonable default and state it; ask only when the choice materially affects the result.
- Never overwrite the source file. Create a clearly named derivative and retain the original filename/context where useful.
- Use available document libraries, APIs, or native document tools that preserve the file type. Avoid fragile find-and-replace across an entire document when formatting, tables, headers, or sections matter.
- For DOCX, inspect paragraphs, tables, headers/footers, hyperlinks, and text boxes if relevant to the task. Avoid adding hidden text, macros, or unnecessary metadata. Preserve meaningful formatting without relying on graphics alone for structure.
- For PDF, scanned files, or legacy formats, distinguish extracted text from visual content and OCR uncertainty. Convert to an editable derivative only when feasible and label conversion limitations honestly.

## Readability and applicant-system resilience

- Prefer selectable text, standard section names, consistent date formats, and a clear reading order.
- Use tables, columns, icons, text boxes, and headers/footers only when the source format supports them reliably and reading order remains clear. Do not claim any format is guaranteed to parse in all ATS products.
- Do not add hidden keywords or keyword blocks. Remove duplication and preserve meaningful context around skills and dates.
- Follow the requested market and format. Avoid personal details that are not needed for the application (including a full home address unless requested).

## Quality check

1. Compare the output against the evidence map. Check every changed factual statement and every number.
2. Check spelling, punctuation, dates, role titles, section order, page breaks, and obvious orphan lines.
3. Render and inspect each page when a suitable renderer is available. Confirm that text is legible, no content is clipped, and page count/layout are sensible. If rendering is unavailable, say so rather than claiming visual review.
4. Confirm that the file opens or can be parsed with the available tools. Do not run tests or upload the document to an external service unless asked.
5. Report the output path, relevant changes, unresolved factual questions, and any validation you could not perform.
